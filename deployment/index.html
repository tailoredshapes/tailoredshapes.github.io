Perspective

From laptop to production

The default assumption for production APIs is a database server, a container orchestrator, and a team to operate them. For many workloads this is the right answer. For many others it is an expensive one that goes unquestioned.

We deployed a 13-entity federated API with event sourcing to AWS Lambda. No database server, no Kubernetes, no container registry. The whole system is a 3.8MB binary that cold-starts in 57 milliseconds. Then we did it twice more, on different storage, without touching the schemas or the clients—and measured each one.

The architecture

Three components: a Rust binary compiled for ARM64, a durable place to put events, and an API Gateway routing requests to the function. The binary contains 13 REST endpoints for writes, 13 GraphQL endpoints for reads, and 19 federation resolvers that join across entities.

The storage layer is merkql, an embedded event log with Kafka-compatible semantics—topics, partitions, consumer groups, append-only writes—backed by files instead of a broker cluster. Every write is content-addressed by SHA-256 and verifiable against a merkle tree, and the log supports temporal queries: read the state of any entity at any point in time.

First attempt: Lambda and EFS

We ran four scenarios against the deployed API: warm single-user CRUD, federated GraphQL queries, concurrent load with 10 users, and write contention with 5 concurrent writers to the same entity type.

The init duration is 57 milliseconds — the time to load and start a 3.8MB Rust binary containing 13 entities, 19 resolvers and a complete event-sourcing storage engine. The remaining ~850ms of the end-to-end cold start is VPC ENI attachment and EFS mount: infrastructure overhead, not application code. Memory peaks at 22MB against the 512MB we allocated; it would run comfortably at 128MB.

Where it breaks

Two hard constraints, and both matter more than the latency numbers.

It is single-writer. The embedded log takes a file lock for write exclusion. That lock serialises execution but not state—each process keeps its own idea of the log tail—so a second writing process is not slow, it is wrong. merkql now detects this and refuses to start, naming the backends that do support concurrent writers. A loud failure is worth considerably more than a quiet one.

EFS is not free and not fast. Each durable write costs an fsync round trip of 50–100ms, which caps the deployment at roughly nine writes per second. Worse, EFS requires a VPC, and a Lambda in a VPC that needs to reach anything else needs a NAT gateway at about $32 a month. The “$0 at idle” claim was never quite true here.

Second attempt: managed Kafka

We deployed the same API—same schemas, same clients, same federation resolvers—against Confluent Cloud. No code changed; we swapped one configuration. Writes got faster and throughput went up about fivefold, but a managed broker bills by the hour whether or not anyone is using it. That solves throughput by abandoning scale-to-zero, which was the point of the exercise.

Third attempt: object storage

The interesting version. merk-aws puts the same log on S3 Express One Zone and appends with compare-and-swap: each write states the offset it expects to land at, and S3 rejects it if another writer got there first. The store arbitrates the tail, which is exactly the job a broker usually does. Many concurrent Lambdas can write one partition with nothing coordinating them, nothing leased, and nothing running between requests.

No VPC, therefore no ENI attachment and no NAT gateway. Cold start is four object reads regardless of how long the log has grown.

Latency is flat in batch size, because the cost is the round trip and not the bytes. Batching therefore costs nothing and buys everything—and a CDC relay or an event handler batches naturally. The same benchmark run from a workstation showed 42ms per flush against 7.4ms from a Lambda in region, which is a useful reminder that most of what people measure as “storage” is actually distance.

Contention behaves the way compare-and-swap always does: one writer on a partition sustained about 1,050 events/sec, eight writers on the same partition about 785, with 49% of appends losing the race, retrying, and being billed anyway. Throughput per partition is capped, so you scale with partitions rather than with writers. That is not a workaround; it is the same advice Kafka gives.

At a batch of 100, a million events costs roughly two and a half cents. If a system generating millions of events does not earn more than that, the problem is not the infrastructure bill.

And when you already have a database

merkpgql is the same log as a set of PostgreSQL tables. It exists because “we already run Postgres” is a stronger argument than any benchmark: there is no new backup policy, no new monitoring, no new compliance sign-off. Writers queue on a row lock instead of colliding, so adding writers neither helps nor hurts—throughput measured flat from one writer to sixteen, where the object-storage backend degrades.

It also does something none of the others can. When the log lives in the same database as your domain data, an event and the write that caused it commit together. The outbox pattern exists because you cannot atomically write to a database and a message broker; when the log is the database, that problem stops existing rather than getting solved.

The part that makes this real

Every backend above claims to be a drop-in replacement for the others. That claim is worth nothing unless it is executable, so we made it executable. There is a conformance suite—27 tests—that compiles inside each implementation. Compiling proves the API matches; passing proves the behaviour does.

It goes further than API shape. Records serialise to identical bytes in every implementation, so merkle roots agree at every size and an inclusion proof issued by one verifies under another. That is what makes moving between them a checkable operation rather than a leap of faith: replay the log into the new backend and compare roots. Equal roots prove nothing was lost, reordered or altered.

The point

The point isn't that every API should run on Lambda, or Kafka, or Kubernetes. It's that the infrastructure becomes a detail you choose late, and can change your mind about.

Start on your laptop with an embedded log. Deploy to object storage when you need a URL and many writers. Move into your own database when transactional guarantees matter more than elasticity. Graduate to a cluster when the log genuinely never goes quiet. The API, the schemas, the clients—they never change.

That's the product.

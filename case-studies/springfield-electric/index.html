Springfield Electric

A utility with an old PostgreSQL, three product teams waiting on it, and a hard constraint: the source system cannot be touched. We put a clean API in front of it and change nothing behind. This one is a worked example rather than a client — the schema, the pipeline and the API are all real and all runnable, so you can check the shape of the answer before you ask us about yours.

The situation

The billing database has been correct and load-bearing for decades. Column names scream, dates are VARCHARs in three formats, and every read path in the business has grown a private opinion about how to parse them.

Three product teams need the same data. The options on the table are a shared ORM library — three copies of the same bugs — or a replatform nobody can sign off.

What we built

A Debezium CDC pipeline reads the write-ahead log and publishes changes into a meshql-managed event log. meshql projects clean domain entities and serves them as REST writes and GraphQL reads. The legacy schema stops at the boundary.

The decisions
and why

Dates get normalised once

Three VARCHAR formats collapse into one ISO-8601 field in the projection. Every date-parsing bug in the estate now has exactly one place left to live.

The log is a table, not a cluster

merkpgql puts the event log in a database the ops team already backs up and monitors — so the work needs no new sign-off, no new on-call rotation and no new budget line.

Writes go through the boundary too

A read-only façade would leave three apps writing legacy SQL, and the mess would grow back. REST writes map through the same domain model, so the boundary holds in both directions.

Result

Three teams build against a documented API instead of negotiating with a schema. The billing system carries on doing exactly what it did before, and nobody has to ask the DBA to approve a migration.

The replatform stays on the roadmap. When it happens, it happens behind the boundary — and the three apps never find out.
